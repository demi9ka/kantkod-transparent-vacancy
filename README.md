# Прозрачная вакансия

Прототип для КАНТКОД: загружает вакансии региона 39 с портала «Работа в России»,
находит неясные условия с помощью GigaChat и сохраняет JSON-отчёт для редактора.
Локальный проверочный режим использует тот же анализатор и не обращается к порталу.

## Подготовка к запуску

### 1. Python и зависимости

Установите Python 3.11–3.14 и откройте терминал в папке проекта.
Активация виртуального окружения не обязательна: команды ниже используют его Python напрямую.

macOS / Linux:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env
```

Windows (PowerShell или CMD):

```powershell
py -3 -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
copy .env.example .env
```

Если `.env` уже заполнен, сохраните его: повторное копирование шаблона не требуется.
На Linux при отсутствии `venv` установите пакет `python3-venv` средствами своего дистрибутива.

### 2. Ключ GigaChat

Впишите в `.env` `GIGACHAT_AUTH_KEY`: готовый ключ авторизации из кабинета GigaChat API,
без `< >` и префикса `Basic`. Это не краткоживущий Access token.
Ключ не нужно повторно кодировать в Base64. `.env` исключён из Git.
Провайдер — GigaChat, модель по умолчанию — `GigaChat-2`; другую доступную модель
можно выбрать через `GIGACHAT_MODEL` после запроса `/models`.

### 3. Сертификаты GigaChat

До первого обращения к GigaChat подготовьте доверенные сертификаты.

macOS / Linux:

```bash
.venv/bin/python scripts/setup_certificates.py
```

Windows (PowerShell или CMD):

```powershell
.venv\Scripts\python.exe scripts/setup_certificates.py
```

Скрипт создаст `certs/gigachat-ca.pem` и выведет строку
`GIGACHAT_CA_BUNDLE=...` с полным путём. Скопируйте её в `.env`, заменив пустое
значение `GIGACHAT_CA_BUNDLE`. Путь формируется для текущего компьютера:
при переносе проекта выполните этот шаг заново.

Сертификат скачивается с Госуслуг по HTTPS и объединяется с доверенной цепочкой
certifi. Системное хранилище не меняется, проверка TLS остаётся включённой.
Не используйте `verify=False`.
[Инструкция GigaChat по сертификатам](https://developers.sber.ru/docs/ru/gigachat/certificates).

## Логи и отладка

При запуске HTTP-сервера и CLI логи автоматически записываются в `logs/app.log`
в кодировке UTF-8. По умолчанию файл и терминал содержат INFO и выше.
Настройки в `.env` (изменения применяются после перезапуска):

```dotenv
LOG_FILE=logs/app.log
LOG_LEVEL=INFO
LOG_CONSOLE_LEVEL=INFO
```

Для подробного файла задайте `LOG_LEVEL=DEBUG`; для подробного терминала — `LOG_CONSOLE_LEVEL=DEBUG`.
Существующий `.env` имеет приоритет над значениями по умолчанию.
`LOG_FILE` можно задать полным путём; относительный путь считается от корня проекта.

На уровне DEBUG для каждой вакансии записываются её ID, исходный JSON, плоский
словарь для модели, текст ответа ИИ и каждое замечание
до проверки. Системный промпт в логи не записывается; один раз за запуск сохраняется только его SHA256.
При сравнении цитаты видны поле, цитата ИИ, исходные значения и результат
совпадения. Представление строк показывает переводы строк и пробелы, чтобы найти
различия в пунктуации и форматировании. WARNING содержит причину отбрасывания.
INFO показывает начало, результат анализа, `finish_reason`, загрузку каждой страницы API,
путь сохранённого отчёта и все выполненные исправления цитат (до/после и метод).

Просмотр файла в реальном времени:

macOS / Linux:

```bash
tail -f logs/app.log
```

Windows PowerShell:

```powershell
Get-Content logs/app.log -Wait -Encoding UTF8
```

При достижении 5 МБ файл ротируется: хранятся текущий файл и до трёх архивов
`app.log.1`–`app.log.3`. Каталог `logs/` исключён из Git. HTTP-заголовки и настройки
авторизации не логируются; ключ авторизации и стандартные поля токенов маскируются.

## Вызовы API

Проще всего вызывать API через Swagger UI. Примеры ниже — для терминала macOS/Linux;
в Windows PowerShell используйте `curl.exe` вместо псевдонима `curl` и команды в одну строку.

```bash
# Проверка доступа к GigaChat
curl --fail-with-body http://127.0.0.1:8000/models

# Проверочный режим: все уникальные вакансии из файла, без запросов к порталу
curl --fail-with-body -X POST http://127.0.0.1:8000/analyze \
  -H 'Content-Type: application/json' \
  --data-binary '@kantkod_sample_vacancies.json'

# Рабочий режим: загрузить вакансии региона и проанализировать
curl --fail-with-body -X POST http://127.0.0.1:8000/runs

# Последний успешный отчёт и состояние запуска
curl --fail-with-body http://127.0.0.1:8000/report
curl --fail-with-body http://127.0.0.1:8000/runs/status
```

`/analyze` принимает JSON-тело в исходном формате API:
`{"status":"200","results":{"vacancies":[{"vacancy":{"id":"...", ...}}]}}`.
Это не multipart-загрузка. В Swagger можно вставить содержимое JSON целиком.
HTTP-запуски синхронные: ответ возвращается после полного анализа.
Долгий запуск можно наблюдать из другого запроса через `/runs/status`.

## Запуск без HTTP-сервера

Используйте Python из `.venv`, в которое установлены зависимости. Активация не требуется.

macOS / Linux:

```bash
# Проверочный режим; лимит MAX_VACANCIES здесь не применяется
.venv/bin/python -m app.cli --input "kantkod_sample_vacancies.json" --output reports/sample.json

# Рабочий режим
.venv/bin/python -m app.cli
```

Windows (PowerShell или CMD):

```powershell
.venv\Scripts\python.exe -m app.cli --input "kantkod_sample_vacancies.json" --output reports/sample.json
.venv\Scripts\python.exe -m app.cli
```

Ошибка `ModuleNotFoundError: No module named 'apscheduler'` обычно означает запуск
другим интерпретатором или отсутствие установленных зависимостей. В macOS/Linux
повторите `.venv/bin/python -m pip install -r requirements.txt` и используйте команды выше;
в Windows — `.venv\Scripts\python.exe -m pip install -r requirements.txt`.

Оба способа запуска используют один процесс анализа. При ошибке CLI возвращает код 1.
После первого успешного запуска с реальным ключом `reports/sample.json` будет
примером отчёта на учебных данных для сдачи. До такого запуска отчёт модели не сгенерирован.

## Структура

Структура следует [Bigger Applications — Multiple Files из документации FastAPI](https://fastapi.tiangolo.com/tutorial/bigger-applications/).

```text
app/
  main.py                # FastAPI, include_router, lifespan, планировщик
  __main__.py            # прямой запуск: python -m app
  dependencies.py        # зависимости маршрутов через Depends
  config.py              # настройки из окружения / .env
  schemas.py             # Pydantic-схемы входа, замечаний и отчёта
  errors.py              # ошибки сервисов
  routers/
    reports.py           # анализ, запуск, текущий отчёт, статус
    gigachat.py           # список моделей
  services/
    gigachat.py           # OAuth, кеш токена, запросы модели
    source.py             # загрузка страниц и проверка входных вакансий
    analyzer.py           # повторы, починка, статусы и объединение замечаний
    vacancy.py            # подготовка плоского словаря
    rules.py              # проверки наличия сведений во всех полях
    quotes.py             # безопасный поиск точной подстроки источника
    reports.py            # общий процесс, дедупликация, сохранение
  cli.py                  # запуск из командной строки
tests/                    # изолированные тесты без расхода токенов
system_prompt.txt         # исходная инструкция для анализа
.env.example              # конфигурация, в том числе расписание
```

Точки входа: `python -m app` (HTTP и расписание), `python -m app.cli` (однократный запуск).
Технологии: Python 3.11–3.14, FastAPI, Pydantic Settings, requests, APScheduler 3.
Один `requirements.txt` для macOS, Windows и Linux. Используется обычный Uvicorn
с `asyncio` и `h11`, без платформенных расширений `uvloop` и `httptools`.
Зависимость `tzdata` обеспечивает часовые пояса для систем без базы IANA, включая
Windows ([документация Python](https://docs.python.org/3/library/zoneinfo.html#data-sources)).
Нативные зависимости Pydantic устанавливаются pip подходящими для платформы пакетами.

## ИИ и проверка результата

Для каждой уникальной вакансии сервис подготавливает плоский словарь и передаёт его в
`POST https://api.giga.chat/v1/chat/completions` вместе с `system_prompt.txt`.
ИИ выявляет пропуски, неоднозначности, противоречия и предлагает конкретные уточнения
по семи темам. Нулевая зарплата и сведения в свободном тексте учитываются промптом.
Текст вакансии помечен как данные, инструкции внутри него не должны исполняться.

Вход модели содержит поля `job-name`, `duty`, `requirements`, `requirement.education`,
`requirement.experience`, `requirement.qualification`, `salary_min`, `salary_max`,
`employment`, `schedule`, `addresses`. Значения — текст или `null` для пустых полей;
числа преобразуются в строки, включая опыт `0`. Адреса объединяются через перевод строки.
HTTP и CLI по-прежнему принимают исходный вложенный формат API.

До обращения к ИИ выполняются детерминированные проверки зарплаты, занятости,
требований и места работы. Они учитывают сведения во всех передаваемых полях:
например, адрес в обязанностях, зарплату в тексте, удалённую работу и признаки
занятости («полная занятость», «неполный день», смены, вахта, ставка).
`0` считается пропуском только у `salary_min`/`salary_max`; опыт `0` — нормальное значение.
Положительные равные границы зарплаты означают фиксированную сумму.
Если указана одна граница, формируется уточнение о неполной вилке.

Пустой `content`, повреждённый JSON и неверный корневой формат вызывают до трёх
повторных запросов после первичного: всего не более четырёх попыток с паузами 1, 2, 4 секунды.
Ошибка одного замечания не повторяет анализ вакансии целиком.

Каждое замечание проходит локальную починку и проверку:

- Для `missing` цитата очищается, но пропуск должен подтверждаться всей вакансией.
  Заполненная минимальная зарплата не может быть объявлена отсутствующей.
- Для `ambiguous` без цитаты сначала проверяются другие поля. При подтверждённом
  пропуске и пустом поле тип меняется на `missing`; при наличии сведений замечание
  отбрасывается. Неопределённый случай получает ровно один точечный запрос починки.
- Однозначные сокращения имён полей приводятся к допустимым. `salary` преобразуется
  в конкретную границу только при однозначном указании в проблеме или цитате.
- Цитаты сравниваются после NFKC, нормализации регистра, пробелов, пунктуации,
  ё/е и латинских двойников. Приближённый поиск через `difflib` использует порог 0,85
  и требует совпадения множеств чисел, отрицаний и слов-условий.
  Результат всегда копируется точной подстрокой исходного поля; та же проверка
  применяется ко второй цитате противоречия. Изменения логируются.
- Пропуски адреса и требований проверяются по всем полям. Замечания о работодателе,
  данные которого модель не получает, отбрасываются. Примеры в рекомендациях после
  «например» удаляются; если рекомендация становится пустой — запрашивается починка.

Результаты правил объединяются с замечаниями ИИ. Дедупликация выполняется по
`(topic, source_field, type)`. Лимит — 6 замечаний: сначала детерминированные,
затем противоречия и остальные замечания ИИ. Дубликаты и превышения лимита отражаются
в `dropped_count` и `dropped_reasons`.
Схема `issues` также передаётся модели в `response_format` с `type=json_schema` и `strict=true`.
Семантические проверки консервативные и эвристические: итоговый отчёт требует проверки редактором.

OAuth выполняется через `requests`, с новым UUID4 в `RqUID`. Токен кешируется
до истечения срока действия; после HTTP 401 обновляется и запрос повторяется один раз.
После исчерпания попыток повреждённый ответ получает `status=error` и причину;
обход остальных вакансий продолжается. Ошибки HTTP, таймауты и ошибки авторизации
не относятся к повреждению содержимого: они завершают запуск ошибкой без повторов
генерации, сохраняя предыдущий отчёт. Ошибка API при точечной починке одного замечания
приводит к его отбрасыванию с причиной, а не к остановке всех вакансий.
Проверка TLS включена. Настройка доверенной цепочки описана в начале README,
в разделе «Подготовка к запуску → Сертификаты GigaChat».

Документация: [авторизация GigaChat](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/gigachat-api),
[генерация ответа](https://developers.sber.ru/docs/ru/gigachat/api/reference/rest/post-chat),
[API «Работа в России»](https://trudvsem.ru/opendata/api).

## Отчёт и сохранность

`REPORT_PATH` (по умолчанию `reports/latest.json`) содержит:

| Поле | Значение |
|---|---|
| `created_at` | Дата завершения в UTC |
| `source` | URL портала либо название локального источника |
| `provider`, `model` | Провайдер и выбранная модель |
| `total` | Число уникальных вакансий |
| `vacancies` | Массив объектов с `id`, `url` при наличии и `issues` |

Замечание содержит `type`, `topic`, `source_field`, `quote`, `problem`,
`recommendation`; для противоречия также `second_field`, `second_quote`.
Ссылки берутся из `vac_url` или `url`, не выдумываются.

Каждая вакансия содержит статус анализа:

| `status` | Значение |
|---|---|
| `ok` | Ответ ИИ получен и замечания не потеряны. Пустой `issues` означает отсутствие замечаний. |
| `partial` | Ответ получен, но часть замечаний отброшена. Даже если отброшены все, статус остаётся `partial`. |
| `error` | Корректный ответ не получен после четырёх попыток. Поле `error` содержит последнюю причину. |

`dropped_count` содержит число отброшенных замечаний, `dropped_reasons` — список причин.
Починенные без потери замечания сами по себе не меняют `ok` на `partial`.
Детерминированные замечания сохраняются и при `error`, но они не заменяют успешный анализ ИИ.
Статусы появились в новой версии: ранее сформированный отчёт следует пересоздать.
Состояние запуска `success` означает, что отчёт сохранён; проверяйте статусы отдельных вакансий.

`examples/report-format.json` — вручную составленный пример формата для одной вакансии;
это не отчёт реального запуска ИИ. Он не заменяет `reports/sample.json` для сдачи.

На один ID сохраняется один результат; при повторе ID внутри входа используется последняя версия.
Каждый запуск полностью заменяет текущий отчёт, не дописывает дубликаты.
Отчёт записывается через временный файл и атомарный `os.replace` после обхода всех
вакансий, включая результаты `partial` и `error`. Недоступность API источника,
ошибки HTTP/сети при первичной генерации и ошибки записи оставляют старый файл без изменений.
Входные вакансии без ID отклоняются. Пустой корректный набор даёт пустой отчёт.

## Источник и расписание

Настраиваются `SOURCE_URL`, `MAX_VACANCIES`, `PAGE_SIZE`, `REQUEST_TIMEOUT`.
По умолчанию загружаются до 100 уникальных вакансий, страницы по 50 записей.
`offset` начинается с 0 и увеличивается на 1 как номер страницы.
При лимите от двух вакансий размер страницы при необходимости уменьшается,
чтобы прочитать хотя бы две страницы при достаточном объёме источника.
В INFO логируется каждая страница: номер, число записей, `offset` и `limit`.
Повторяющаяся без новых ID страница считается ошибкой; GET-запросы повторяются
при временных сетевых ошибках и HTTP 429/5xx до двух раз.

В `.env`:

```dotenv
SCHEDULE_ENABLED=true
SCHEDULE_CRON=0 9 * * *
TIMEZONE=Europe/Kaliningrad
```

APScheduler запускает рабочий режим ежедневно в 09:00 по Калининграду,
пока работает FastAPI. Пропущенные при выключенном сервисе запуски не восстанавливаются.
Ручной и плановый запуск используют один метод `ReportService.run`.
Повторный одновременный запуск возвращает HTTP 409. Статус хранится в памяти,
отчёт — на диске.

Запускайте **один worker и один экземпляр сервиса**; не запускайте CLI одновременно
с HTTP-анализом в тот же файл. Блокировка процесса и планировщик рассчитаны на один процесс.
Для разработки можно использовать `--reload` при выключенном расписании.
API предназначен для локального запуска; публичный доступ требует отдельной авторизации
и ограничения запросов, поскольку каждый анализ расходует квоту модели.

Конфигурация автоматизации: `.env.example` и создание job в `app/main.py`.
Для запусков по расписанию оставляйте терминал с сервером открытым и компьютер включённым.
